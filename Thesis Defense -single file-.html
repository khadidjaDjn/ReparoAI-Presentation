Introduction

Context

Fault diagnosis is a knowledge-intensive task: It relies on expert knowledge and the consultation of technical documentation to identify possible causes and appropriate repair actions.
Large language models can read a fault described in plain language, but their knowledge is fixed at training time and they state unsupported causes with full confidence.
Problématique. How can we build an intelligent assistant that understands a fault described in the user's own words, and diagnoses it from real repair evidence?

Making sure the generated data can be trusted

01
Don't make things up
The model is told not to invent error codes or numbers it wasn't given.
02
Be extra careful with cosmetic parts
Covers, frames, bezels rarely mean a real functional fault, so the model is warned not to assume one.
03
Check the output is well-formed
Every answer is parsed and checked against the expected structure before it's accepted.
04
Try again if it fails
Up to 3 attempts; guides that still fail are logged and skipped instead of blocking everything.
05
Ask twice and compare
The model runs twice; if the two answers disagree too much, the result is marked low-confidence.
06
Double-check cosmetic claims
If the original guide never mentions a real failure, the record is force-flagged low-confidence, no matter what the model said.
07
Keep track of everything
Every record keeps an ID and a version number, and every skipped or excluded guide is logged with a reason, so the dataset stays auditable.

WHY RERANK?
Retrieval provides a candidate pool, but not necessarily the best ordering.
The cross-encoder evaluates the query and candidate together for more precise relevance scoring.
Only the best-ranked evidence is passed to the LLM for grounded generation.
KEY IDEA
Retrieve broadly → rank precisely → generate from evidence.

GraphRAG Module

Knowledge Graph Construction

Vocabulary construction: different phrases for the same problem are grouped under one unifying tag, for symptoms and for diagnoses.
Guide tagging: each guide is assigned its relevant tags using an LLM model (Qwen3-4B-Instruct, 92% exact match accuracy).
Tags as nodes: every tag becomes a Symptom or Diagnosis node, so guides describing the same fault link to the same node instead of fragmenting into near duplicates.

Knowledge Graph Enrichment and Embeddings

Every symptom and diagnosis node carries a canonical tag, for example not_charging.
For each node, a short text is built from the tag with its synonyms and user phrasings, encoded into a dense vector, and stored on the node.
Run once at build time, so free text queries can later reach a tag without exact keyword overlap.
Two embedding models were compared for symptom linking: all-MiniLM-L6-v2 (384 dimensions) and BGE-base-en-v1.5 (768).
Nodes and queries use the same model, and embeddings are normalised to unit length, so similarity depends on direction rather than magnitude.

ENTITY LINKING
A threshold discards weak matches and a cap limits how many symptoms one query may link.
Links keep their similarity scores rather than being binary, because the evidence lies in the combination of symptoms.
GRAPH TRAVERSAL
Two hops. A guide is reached whenever it shares at least one symptom. How completely it matches is quantified in scoring.
Traversal walks guide level structure, so the guide in which a symptom and a diagnosis meet is preserved.
24 / 37

Guide Scoring and Diagnosis Aggregation

Guide score
How completely a guide accounts for the symptoms reported. Matching all of them scores highest, so guides explaining the whole combination beat guides matching one symptom in isolation.
Diagnosis evidence
Guides pointing at the same diagnosis accumulate. A guide listing several diagnoses is expressing uncertainty, so its evidence is divided rather than counted in full for each. Scores are normalised to sum to one.
Confidence signal
Read from the gap between the top candidate and the next one, not from the absolute value. Candidates too close together trigger a clarifying question rather than an answer.

Generating

Evidence-Grounded Generation

The role is narrow by design: the model reads the assembled evidence and expresses a grounded answer. All diagnostic evidence comes from retrieval.
GraphRAG, closed set: the model selects from the candidates the graph retrieved and cites the guides behind its choice. Any diagnosis outside that set is ungrounded by construction.
Hybrid RAG, passage supported: passages are returned rather than an enumerated set, so the diagnosis must be supported by them and cite them.
The output is structured, not free prose, so faithfulness and citation validity can be checked automatically.
Three instruction-tuned backbones compared under identical prompting: Qwen2.5-7B, Llama-3-8B, Gemma-2-9B, all 4-bit.

Discussion of the end-to-end results

Accuracy on hits. Even when both strategies retrieve the correct diagnosis, the models select it more reliably under GraphRAG (0.90 to 0.94) than under Hybrid RAG (around 0.75).
Retrieval strategy dominates. The three backbones differ by two to three points within a strategy; changing strategy moves accuracy by ten or more.
The lever is the evidence, not the model. As in the embedding comparison, gains come from what is retrieved rather than from what consumes it.

Conclusion

Limitations

The corpus is dominated by smartphone related cases, so coverage of other electronic categories, and of true board level circuits, is thin.
The iFixit diagnostic layer is inferred from repair procedures rather than observed directly, a gap the confidence handling procedure flags but does not eliminate.
The held out evaluation set, though manually verified, is modest in size.
The output is fundamentally retrieval limited: the assistant returns the closest matching repair guide rather than generating a procedure of its own, so its answers are bounded by what the corpus already contains.
The pipeline is English only, so a query phrased in another language falls outside what either retrieval strategy can currently match.
35 / 37

Future Work

Evidence base: broaden the corpus and the graph to more device categories and to genuine circuit level data.
Multilingual retrieval: extend the pipeline to queries phrased in other languages.
Multimodal evidence: incorporate schematics and board images alongside text.
Graph reasoning: extend traversal beyond symptom to diagnosis paths.
Evaluation: scale to a larger benchmark to strengthen confidence in the reported results.
Generation: fine tune a model on the repair corpus so the assistant can generate repair guidance for a case directly, rather than only retrieving the nearest existing one.
